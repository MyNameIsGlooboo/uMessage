How to work through it

  1. Finish phase 0 first (tidy and ship the review branch).
  2. All five decisions are answered, so nothing blocks phases 1 to 3.
  3. Phases 1 to 3 are UI and Material 3 work. Their item groups touch different files, so each group can go to its own agent in its own worktree.
  4. Phase 4 is a staged rebuild of the architecture. It touches the same large files as phase 3, so it starts after phase 3 is merged. Its first stage (B0) adds the tests every later stage is checked against.
  5. After every phase: :app:testFossDebugUnitTest, :app:lintFossDebug, :app:assembleFossRelease, then an emulator check in light and dark, English and Persian, at font scale 1.0 and 1.3. The phone gets install-and-look checks only.

Phase 1 — typography and line height

Files: ui/theme/Type.kt, ui/thread/ThreadComposer.kt, ui/conversations/ConversationItem.kt, ui/thread/ThreadBubbles.kt, font resources. One agent.

highT1 Add the Material 3 line-height style to every text style. The heading() and body() helpers in Type.kt leave out lineHeightStyle, so Compose trims the first and last line. Measured on the emulator: bodyMedium lines take 43 px instead of 52 px (20 sp), and titleMedium takes 53 px instead of 63 px (24 sp). Text in rows, buttons and chips sits tighter than spec and is not centred like stock M3.
Fix: add lineHeightStyle = LineHeightStyle(LineHeightStyle.Alignment.Center, LineHeightStyle.Trim.None) to both helpers (the value Material 3's own type tokens use).
Done when: English and Persian preview lines have the same height (52 px at 420 dpi), and row padding still looks balanced. Re-check list row spacing, the chat bubbles, buttons, chips and the snackbar.
highT2 Persian text uses a fallback font with different metrics. Roboto has no Arabic-script glyphs, so Android draws Persian with a system fallback. A Persian line measured 61 px against 43 px for English, so Persian rows have a larger name-to-preview gap and a lower badge. T1 fixes the height. Bundle Vazirmatn (decision D3) as static Regular, Medium and Bold files under res/font, add its licence to the third-party notices, and use it for Arabic-script text (a font fallback chain or a FontFamily chosen by script).
Done when: a list with mixed English and Persian rows has identical row heights and baselines, in both the list and the chat screen.
lowT3 Composer labels squeezed below the type scale. ThreadComposer.kt:307 and :312 set labelSmall to lineHeight = 13.sp (M3 is 16 sp) so the MMS label and the character counter fit in 48 dp. Use the plain style and let the field grow, or show the counter only, as Google Messages does.
medT4 In-app font-size setting stacks on the system font size. scaled() in ConversationItem.kt and ThreadBubbles.kt multiplies size and line height by a Fossify setting. Decision D1: remove the setting, its preference and the scaled() helpers, and drop setFontScale from ConversationsViewModel. Existing stored values are ignored.
lowT5 Hard-coded text sizes in the Fossify Commons screens still used by the app: ManageBlockedNumbersScreen.kt:412 and :423 (16.sp, no line height). Replace them with type-scale styles (they go away anyway if the screen is replaced, see M5).

Phase 1b — spam filter

highF1 Do not auto-allow code messages with links (decision D4). Now that "Allow verification codes" is on by default, the exemption must not let "code + link" phishing through. In DefaultSpamFilter, apply the exemption only when the body looks like a code and either has no link or is in the origin-bound format (last line @host #code, as used by WebOTP and the SMS Retriever). Otherwise fall through to the normal mode decision.

Rules for every stage

  • One stage at a time on its own branch; each slice is a reviewable PR.
  • B0 tests, lint and the minified release build pass before every merge.
  • Emulator check of the touched screens in light and dark, English and Persian; phone install-and-look check before each merge.
  • The receive path (SmsReceiver, MmsPushReceiver, SmsDelivery) changes only together with its B0 tests in the same PR.
  • B2 to B4 may overlap only when they own different screens; B5 starts after B4.
